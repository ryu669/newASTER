## 2. 初回完成見本の進行

```text
タイトル → はじめる／つづき → 拠点
拠点 → 編成・装備 → 作戦 → 準備任務（任意）→ 方舟討伐
討伐 → 結果・報酬保存 → 拠点 → 武器整備／記憶／会話 → 再挑戦
```

- 初期加入はセラ・リネ・アシュ。初期順は防御→支援→攻撃、遺物3種は最初から選べる。
- 討伐等で敵の歌と同行ヒロインの歌を取得し、それぞれの物語を解放する。拠点で本人を配置して交流し、好感度と物語条件で個別シーンを開く。具体条件は追加仕様に従う。
- 翼破壊討伐後の整備と再挑戦に加え、歌の物語を読む→本人を拠点に配置→交流→個別シーン解放→回想までを完成見本の必須確認に含める。読了や最大育成を次の戦闘の必須条件にはしない。
- 好感度・歌・シーンの追加に伴い、従来の8～15分という全体所要時間は再見積りする。最初の討伐から1人のシーン解放までと、全員分の収集・読了を別々に測る。
- 拠点は固定カメラとメニュー、少女の待機動作で表現。歩き回る操作や建築は作らない。
- 日本語、マウス＋キーボード。ゲームパッドは初回完成見本の必須項目にしない。

### 物語の短い芯

「帰る場所を失った人々のため、地上へ降ろされた鐘」を探して、少女たちは空を巡り続ける方舟に近づく。ボスは単に壊す相手ではなく、かつて人を運んだ遺構として描く。初回記憶は試作の文章を引き継ぎ、リネが鐘の音を知っていると明かす会話で次の空域への動機を作る。これは独自の仮設定であり、続編の大量の台詞はまだ制作しない。

## 3. 戦闘計算と演出の境界

### 状態と時計

戦闘状態は`Running / Decision / Chain / Victory / Defeat`。Pauseはこれらと独立したフラグにする。戦闘時計は1刻み50msの整数で扱う。12秒は240刻み、託す2秒は40刻み。描画フレーム数を攻撃頻度に使わない。

Runningだけ戦闘時計を進める。Decisionは判断時間無制限、Chainは技を順番に解決するが戦闘時計は進めない。演出時計は別管理とし、通常表示・短縮表示のどちらでも同じ順の技を一度ずつ適用する。演出終了通知が来ない場合にも中断・短縮操作で先へ進める設計にする。

アプリの非アクティブ化、Escメニュー、会話・ヘルプで両時計を停止する。復帰時は手動再開し、離席中の時間を追いつき処理しない。フレーム落ち時も行動を捨てず、未処理の戦闘刻みを順に処理する。極端な停止は一時停止へ移す。

### 同時刻の順序

1. 時刻に到達し、効果の期限・部位の開閉状態を評価する。`現在 < 終了時刻`のときだけ有効。
2. 味方通常攻撃を編成順に処理。1行動ごとに勝敗を判定。
3. 敵の通常攻撃、次にボスの特殊行動を処理。各被害に防壁→吸収→HP減少→救援を適用し、勝敗を判定。
4. 指示時刻ならDecisionへ。すでに勝敗が決まっていたら指示を出さない。

演出中はこの順序を入れ替えない。全体攻撃と救援は試作同様に編成順で処理し、HP0の対象を蘇生しない。勝利・敗北後は残りの攻撃、次の技、予約を実行しない。

### 計算と表示

- 基本のHP・攻撃・技倍率は試作を移植し、まず一致させる。新しい敵や武器はその後で追加する。
- 最終ダメージ・回復の丸めは非負の値を四捨五入。C#の既定丸めに任せず、0.5を切り上げる試験を入れる。乗算の途中では丸めない。ただし吸収前の被害整数化は試作通り。
- 技の予告は同じ計算機を状態のコピーに対して使い、実状態を変更しない。予約済みの強化・部位破壊・回復上限を順に反映する。
- 飛行座標と物理衝突をダメージの条件にしない。技開始でActorとTargetを確定し、命中演出で確定済みの結果を表示する。
- 通常の技は1回の効果適用。見た目を多段にしても追加ダメージを勝手に発生させない。
- `SkillStarted / DamageApplied / Healed / PartBroken / RescueUsed / BattleEnded`に連番、戦闘刻み、人物ID、対象ID、値を持たせる。日本語ログから数値を抽出しない。
- バックエンドはC#の独立した層。UnityのGameObjectやAnimatorを戦闘ルールへ渡さない。

### 操作

画面下に味方3人のHPと状態、右に候補・参加順・効果予告・発動／託す。上にボスと部位HP、次の攻撃対象と残り時刻。解放は既定OFF、発動または託すの確定でOFFに戻す。

マウスを基本とし、Enter＝発動、T＝託す、O＝誓い解放の切替、Space＝一時停止／再開、Esc＝メニューの候補とする。メニューや入力欄が開いている間は戦闘ショートカットを無効にする。押しっぱなしの連打を受け付けず、画面のボタンと同じ可否判定を通す。

## 4. 最大連携以外を選ぶ検証条件

本番の方舟を急に難しくせず、別の診断用作戦で比較する。以下はまだ未実装の試験条件であり、バランス検証済みではない。

| ケース | 設定案 | 比較と合格条件 |
| --- | --- | --- |
| 強打前の防壁 | 12秒にセラへ指示、14秒に全員へ強打140、予告は8秒。以後は仮に24秒周期 | 即発動は強打を軽減、託すと防壁が間に合わない。HP差と遺物の吸収が予告・実結果で一致 |
| 砲口の露出 | 12秒以上15秒未満に露出。露出中の攻撃技だけ1.5倍。通常攻撃は変えない | 攻撃役先頭の単独発動と2番目の2人発動が成立し、3番目の16秒発動は機会を失う |
| 連携を伸ばす余裕 | 12～18秒に強打・露出終了なし | 防御→支援→攻撃の連携に火力上の価値が残る |
| 温存の価値 | 誓い2以上、長い安全区間と近い危険区間を別に作る | 解放の一律優位なら、保持効果か敵の設計を見直す。現行の10%保持を確定値としない |

診断用の高被害は通常難度の決定値ではない。比較は同じ初期状態・編成・装備で入力だけを変え、勝敗だけでなく被害、生存、討伐時間、入力回数を記録する。砲口の条件を満たせる候補が参加していない場合は、UIに攻撃可能とは出さない。

P0の終了条件は、早期発動と最大連携がそれぞれ有効な状態を再現し、ユーザーがその理由を表示から読み取れること。試験ケースを通すだけで、1戦全体の面白さを確認したことにはしない。

## 5. 育成・準備・報酬の着手値

移植一致の検証モードは旧試作の星片・全体強化をそのまま使う。本制作モードは別の進行データとし、一律強化を必須育成として重ねない。

| 項目 | 完成見本での規則 |
| --- | --- |
| 素材 | 星片と翼片の2種 |
| 討伐報酬 | 本体撃破で星片3。翼を壊して勝利すると星片＋1、翼片1 |
| 敗北・撤退 | 報酬なし、素材消費なし。翼だけ壊して撤退しても翼片なし |
| 武器分岐解放 | セラだけ、星片4＋翼片1で2分岐を一度に解放。分岐の切替は拠点で無料 |
| 守りの分岐 | セラの防壁時間＋2秒。半減するのは引き続き次の1撃 |
| 支援の分岐 | セラの崩しを20%→25%へ置換。加算して45%にはしない |
| 歌・物語・個別シーン | 敵と本人の歌は別収集。好感度とシーンを人物別管理。取得・解放・読了を別保存 |
| 準備任務 | 方舟の一部を使う短い任務。初回成功で対方舟の弱体化を恒久解放 |

準備任務は繰り返し必須にせず、初回は飛ばして直行できる。弱体化の解放後は追加の解放報酬を重複付与しない。出撃時に編成・装備・弱体化を固定し、途中で変更しない。

これらは初回完成見本の値。6人・3ボス分のドロップ表や長期育成を先に埋めず、最初の武器選択が戦い方を変えるかを見て拡張する。

## 6. セーブと異常時

主人公は両作品終了後の同じ観測者であるプレイヤー。開始時に入力する名前を `playerProfile.displayName` として保存する。名前変更で人物IDや進行を変えない。名前入力・改名・旧セーブの扱いは[プレイヤー名仕様](continuity-opening.md)に従う。

Windowsの保存場所はUnityの`Application.persistentDataPath`を使用し、Company/Product名を固定する。APIは継続保存用ディレクトリを返す。[Unity公式説明](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Application-persistentDataPath.html)。想定名はCompany=`newASTERLocal`、Product=`newASTER`。実際の保存先は設定画面から開けるようにする。

`save.json`を1枠、直前の正常データを`save.backup.json`、書込途中を`save.tmp`として区別する。設定は`settings.json`へ分離。改造対策や暗号化は実装目的に含めない。

必須項目は`schemaVersion / revision / contentVersion / currencies / roster / formation / equipment / clearedOperations / unlockedMemories / readMemories / readDialogues / lastCommittedBattleId`。人物や装備は表示名ではなく安定したIDで参照。金額・素材数の負値、不明なID、編成の重複を検証する。将来版のschemaVersionを古い版で勝手に初期化しない。

保存タイミングは報酬確定、整備、編成変更、拠点配置、交流・シーン読了。歌の所持、人物別好感度、拠点配置、未使用交流権、物語とシーンの解放・読了、初回報酬処理済みIDを追加仕様に従って保存する。操作の連打を直列化する。報酬を含む新しい状態をメモリ上で一度作り、tmpへ書込→読戻し検証→正常ファイルをバックアップして置換、の順で確定する。戦闘IDと報酬を同じ保存単位に入れ、再試行では同じ状態を保存して報酬を加算し直さない。

| 問題 | 動作 |
| --- | --- |
| 保存失敗 | 現在の状態と未保存の結果をメモリに維持。「再試行」を出し、未保存と明示。結果画面からの離脱前にも知らせる |
| 現行ファイルが破損 | バックアップを検証し、日時・進行を表示して復旧を選べるようにする |
| 両方破損 | 新規開始を明示選択。元ファイルを残し、自動で上書きしない |
| 書込中の終了 | 次回起動で正式ファイルを優先して検証。tmpを完成データと決めつけない |
| 二重起動 | 同じ進行データへの同時書込を許さず、後から起動した画面で既存実行を案内 |
| 戦闘中の終了 | 途中戦闘は再開せず、最後に保存した拠点へ戻る。報酬未確定なら獲得なし |
| ブラウザ試作のデータ | 自動取込しない。試作の保存領域は維持し、本制作は新しい進行として開始 |

## 8. 性能・設定の目標

手元PCでまず1920×1080、ウィンドウ表示、60fps上限、VSync ON、画質中。これは初期設定案であり、現在のモニター解像度を読み取った結果ではない。

画質は低・中・高、表示はウィンドウ・ボーダーレス。音量は全体・BGM・SE、カメラ揺れはON/OFF、演出は通常・短縮、UI文字は標準・大。適用できない解像度は選択肢に出さない。最初は音声・キー再割当・多数の描画項目を増やさない。

基準シーンは味方3人、方舟、雲、通常エフェクト、UIが同時に出る状態。開発用EditorではなくWindowsビルドで計測し、通常区間の95%のフレームが16.7ms以下を仮目標とする。ロード・起動・最初のシェーダー準備は別測定し、技を繰り返した際の停止・メモリ増加も見る。未達時は影、透明エフェクト、描画距離を順に比較する。

ネット接続なしで初回起動、素材読込、セーブ、終了、再起動が通ることを完了条件にする。ストリーミング配信素材、リモート設定、分析データ送信は導入しない。

## 10. 移植照合データ

`tests/fixtures/battle-parity-v1.json`に旧試作の初期状態、入力列、各入力後の期待状態、報酬を保存。`tools/battle-parity.mjs`で生成・照合する。

```sh
node tools/battle-parity.mjs
```

6ケースは翼おまかせ80秒、翼温存64秒、翼解放62秒、本体・並べ替え52秒、強化3・解放42秒、低HP診断の敗北15秒。敗北報酬0と勝利報酬の二重取得防止も確認する。最後のケースだけ初期HPを1に設定した診断であり、通常出撃の結果ではない。

JSONの操作は`step(delta=0.05,count=N)`、`entrust`、`fire(release=bool)`。checkpointsはoperationsと1対1。C#側はstep回数を同じにし、状態の値を比較する。浮動小数の内部誤差を除くため戦闘時刻は整数刻みに対応させ、HP・部位HP・回数・フラグ・順番は完全一致を求める。

基準ファイルには戦闘エンジンのSHA-256を付ける。ゲームルールを変えて不一致になった場合、基準を無条件に上書きせず、差分を意図した変更として確認する。明示再生成は`node tools/battle-parity.mjs --write`。この基準は旧試作の移植用であり、未実装の強打・露出・武器分岐の合格証明ではない。
