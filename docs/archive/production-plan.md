## 1. 推奨する本作の形

**巨大な空中遺構を、少女たちの連携で討ち、遺物と記憶を持ち帰るRPG。**

『巨神と誓女』からは、巨大な敵との反復戦闘、連携の高揚、敵の物語を集める動機。『ANGELICA ASTER』からは、3D空中演出、ジョブの判断の違い、装備と作戦による攻略、仲間のいる拠点を取り入れる。原作の画面や固有設定を再現するのではなく、この体験の組み合わせを独自の世界と素材で作る。

オフラインで完結し、手元のWindows PCで遊ぶゲームとして制作する。プレイ時のログイン・通信・外部サービスを必須にせず、必要な素材をローカルに揃える。アカウント、運営サーバー、クラウドセーブ、課金機能は作らない。配布・販売・ストア対応・インストーラー・自動更新は現時点の制作範囲から外す。開発用エディターを起動せず遊べるローカル実行ファイルは作る。

通常は戦いを眺め、判断時には戦闘時間を停止。飛行は自動演出で、移動・回避の手動操作は加えない。3D化で増やすのは迫力と人物への愛着であり、操作負担ではない。

## 3. 先に直す戦闘の課題

### 発動のタイミングを変える3種類の敵

| 敵の仮案 | プレイヤーの判断 | 最大連携以外の価値 |
| --- | --- | --- |
| 鐘を失くした方舟 | 翼を折って安全にする／本体を急ぐ | 入門。現在の敵を引き継ぐ |
| 鎧殻の砲塔 | 予告された砲口の露出中に攻撃技を当てる | 待つと露出が終わるため、単独・2人発動と編成順が重要 |
| 記憶を運ぶ繭 | 連続攻撃に防御と回復を分けて合わせる | 全員の技をまとめて使い切るより、別の指示機会へ分散する価値 |

名称・行動・数値は独自の仮案。まず後ろ2種を仮図形で比較し、すべての敵を「最大連携への罰」にしない。長い安全区間には3人連携の強さを残す。

タイミング例：12秒の指示でセラが候補、14秒に敵の強打。即発動なら防壁が間に合い、託すなら強打の後に次の指示になる。試作の「同時刻は通常行動→指示」を引き継ぎ、表示でも順序を明示する。

砲口が12～15秒に開く例では、攻撃役が先頭なら12秒に単独発動、2番目なら14秒に2人連携、3番目なら16秒となり間に合わない。攻撃役が今の候補でないのに「今発動すれば攻撃できる」と案内しない。敵の予告時刻は出撃前にも示し、初見の暗記必須にはしない。

### 資源とジョブ

現行の「誓い」を共通資源として残し、まず敵の違いで温存と消費を比較する。全員に弾・球・ハートを同時に追加しない。防御は被害を防ぐ時刻、支援は回復と1回限りの救援、攻撃は短い露出中の放出で個性を作る。

それでも攻撃役の判断が単調な場合に限り、4人目の射撃役で独立した準備資源を比較する。試作済みの共通資源を削るか残すかも含め、管理項目を増やす前に試す。

連携の上限は3人。長い連携の見せ場は、一人の技の多段攻撃や締めの演出でも表現できる。「参加人数」と「ヒット数」は別表示にし、確率追撃は基本の判断が成立してから検討する。

自動操作は「即発動・資源温存」を基本とし、後に「安全優先／連携優先」を選択可能にする案。何を消費するか出撃前に説明する。初回攻略は手動の判断、習熟後の素材集めは短縮演出・再戦の手軽さを重視する。

## 4. 3Dの完成イメージ

アニメ調の少女と、古い機械・建造物・生物的な部位が混じる巨大な遺構。人物は顔と輪郭を明瞭にし、敵は大きなシルエットと部位で読み分ける。空には雲、遠い地形、浮遊する残骸を配置し、距離を伝える。

| 状態 | 見せ方 | 読みやすさの条件 |
| --- | --- | --- |
| 通常戦闘 | ボスを斜め下から見る基本カメラ。味方は手前・横に浮遊 | 攻撃対象と味方HPが常に分かる |
| 指示待ち | 安定した構図へ戻り、対象部位と参加者を強調 | 時間が止まっていると分かる。カメラを勝手に回さない |
| 個人技 | 顔または武器→対象への接近→着弾→帰還 | 攻撃部位が変わっても人物と対象を見失わない |
| 連携 | 次の人物へ視線を渡し、最後の一撃で敵を広く見せる | 通常3人連携は計3～5秒を仮目標。短縮時は1～2秒 |
| ボス大技 | 発射口や部位の予備動作→引き画で大きさを示す | 警告と状態表示を演出で覆わない |
| 撃破 | 部位の崩壊、光、静かな余韻から記憶へ | 再戦では省略可能 |

全体・人物・対象部位・大技の4系統のカメラを基本に、ボスごとの撮影位置をデータとして持つ。自由な飛行空間の衝突解決を先に作り込まず、対象別の接近・帰還経路を使う。ゲーム判定は座標の物理衝突に依存させない。

カメラの揺れ軽減、演出短縮、ダメージ表示の見やすさを最初の完成版から設定可能にする。演出速度・省略によってダメージ、効果時間、敵の行動数が変わらない構造を守る。

## 5. 最初の製品規模と、その前の完成見本

本制作は、製品と同じ品質で小さな一部分を完成させる「完成見本」を先に作る。

| 項目 | 先に作る完成見本 | 小規模な初回製品案 |
| --- | --- | --- |
| 味方 | 現在の3人、全員3D | 6人から3人を編成 |
| ボス | 方舟1体を完成品質。別行動1種は仮モデルで検証 | 攻略の違う3体。形状違いだけの水増しは避ける |
| 行動・演出 | 基本技3、接近帰還、敵大技、翼破壊、撃破 | 6人それぞれの基本技と共通化できる移動・反応 |
| 育成 | 遺物3種、武器分岐を1人分試す | 遺物6種、各人の武器2分岐。付け替え・振り直し可能 |
| 作戦 | 準備→ボス→記憶の小さな選択画面 | 3空域、各空域に任意の準備・ボス・記憶の3ノード |
| 拠点 | 3枠へのヒロイン配置、交流、好感度、整備、歌の物語と回想 | 加入済み全員を入れ替えて配置・交流できる |
| 物語 | 方舟の歌3章、各ヒロインの歌第1章と個別シーン各1本 | 敵の歌各3章、ヒロインの歌各3章＋個別シーン各3本、導入と結末 |
| 音 | 戦闘・拠点BGM、攻撃・UI・部位破壊の基本SE | 曲・効果音を拡充。全編音声は別枠 |
| 想定体験 | 初回20～30分を目標に検証 | 初回2～3時間を目標。周回は任意 |

時間は制作・遊びの見積りを確定したものではなく設計目標。プレイ時間を延ばすための必須周回は作らない。準備ノードは短い既存素材の派生遭遇として予算化し、3体以外の新規ボスモデルを前提にしない。

準備作戦で得る弱体化は、効果と対象を明示し、ボス選択時に有効／無効を切替できる案。弱体化なしで勝つ選択も残す。素材は共通素材とボス固有素材程度から始め、初勝利や部位破壊で確定入手させる。物語の主要部分も初回・明示された実績で確定解放する。

育成は「武器で得意分野を伸ばす」「遺物で運用を変える」の2層。試作の一律3段階強化は検証用として扱い、製品でさらに重ねて必須育成を増やさない。

## 6. 技術方式：Unityを第一候補にする

Windows 3D、人物アニメーション、カメラ演出を中心にするため、**Unity 6系＋URP＋Cinemachine＋Timeline**を第一候補とする。これは今回の要求からの設計判断であり、原作がUnityだから必須という意味ではない。

URPは幅広い機種向けの描画を対象にする公式描画基盤。[公式説明](https://docs.unity3d.com/6000.0/Documentation/Manual/universal-render-pipeline.html)。カメラ制御に[Cinemachine](https://docs.unity3d.com/Packages/com.unity.cinemachine@3.1/manual/index.html)、演出の時間構成に[Timeline](https://docs.unity3d.com/Packages/com.unity.timeline@1.8/manual/index.html)を検討する。採用バージョンは制作開始時に組合せとサポート期間を確認し、Editorとパッケージを固定する。参照文書の番号をそのまま最新版として採用しない。

Godotも候補だが、今回は2つのエンジンで同じ完成見本を作らず、最初の人物取り込み・撮影・WindowsビルドでUnityの適合性を判断する。利用経験、制作担当者、使用予定素材が別エンジンに強く偏るなら再比較する。利用費・素材予算は担当人数と素材の調達方法が分かってから確認する。

### 引き継ぐものと作り直すもの

| 現在のもの | 扱い |
| --- | --- |
| `src/engine.mjs` | ルールとテスト結果を移植基準にする。JavaScriptをそのままUnityへ持ち込まない |
| テスト30件、時間・状態の測定 | C#側の回帰試験へ移す。代表戦闘の入力列と結果も比較する |
| `src/main.mjs`・HTML・Canvas | ブラウザ試作として保存。製品の画面・演出は作り直す |
| 遺物・役割・ボス・会話 | 固定分岐から定義データへ。安定したIDで参照 |
| localStorage | 製品は版番号付きのファイル保存とバックアップへ。ブラウザ試作の自動移行は前提にしない |
| 原作の本体・動画 | 調査資料としてのみ使用。モデル・テクスチャ・音声は製品へ同梱しない |

戦闘計算は描画に依存しないC#の層に分離する。固定刻みの戦闘時計と、演出用の時計を分ける。入力→戦闘状態とイベント→画面・アニメーションの順に処理し、アニメーションの終了通知だけに勝敗や報酬を依存させない。

試作の文章ログをパースして演出せず、`SkillStarted`、`DamageApplied`、`PartBroken`、`BattleEnded`のような型付きイベントを使う。人物ID・部位ID・値を渡し、表示文は画面側で作る。

ボス定義は部位、予告、行動、フェーズ、報酬を分離。個別敵名の条件分岐を大量に足す前に、方舟と砲塔の2種類が同じ仕組みで表現できるか確かめる。初回は万能なスキルエディターを作らず、必要な効果だけをデータ化する。

保存は進行・編成・装備・設定を対象にし、一時ファイルからの置換、前回バックアップ、旧版からの移行試験を用意する。戦闘途中の復帰は初回完成見本では対象外。報酬確定の二重実行を防ぐ。

現在のブラウザ試作はルートに残し、Unityプロジェクトは新しい`game/`ディレクトリに置く案。3D元データと書き出しファイルを区別し、大きな制作素材はGit LFSの対象を決めてから追加する。今回は構成案のみで、移動・エンジン導入は行っていない。

## 7. 3D制作で最初に通す工程

キャラクター1人について、設定画→モデル→骨格→飛行待機・攻撃・被弾・帰還→表情→エンジン取込→撮影→Windowsビルドまで一周する。立ち絵ができたことと、ゲームで使える3D人物ができたことを区別する。

完成見本の素材台帳には、人物3体、固有武器3、翼・髪・衣装の可動、顔の表情、ボス1体と破壊部位、空域1、拠点1、技3、大技1、UI、BGM・SEを列挙する。各素材の担当・出典・編集可否・完成基準を残す。

共通の骨格と基本動作を使い、技の決め姿・武器・表情で人物を区別する。ボスは外殻・翼・核などの部品に分け、破壊前後の見た目を用意する。顔が接写に耐えるか、翼と武器が重ならないかを、量産前に判断する。

描画品質の仮目標は手元のプレイ用PCで1080p・60fps。現時点の性能保証ではない。ユーザーが使うPCと表示解像度を基準に、実行ファイルでフレーム時間・メモリ・読込を測る。広範な配布先向けの最低動作環境策定は行わない。透明な雲やエフェクト、影、スキンメッシュを個別に評価し、遠景の簡略化も使う。[UnityのLOD Group](https://docs.unity3d.com/6000.0/Documentation/Manual/class-LODGroup.html)は距離等に応じた詳細度管理の候補。

## 8. 制作順と進行判定

| 段階 | 作るもの | 次へ進む条件 |
| --- | --- | --- |
| P0：戦闘の判断を検証 | 試作側で砲口露出・連続攻撃の仮パターン、単独／連携／状況判断の比較 | 同じ編成でも早期発動が有効な場面と3人連携が有効な場面を再現できる |
| P1：3D制作工程を確認 | 人物1、仮ボス、飛行と接近、カメラ4系統、Windowsビルド | 大きさ・顔・対象が伝わり、モデル取込と性能測定を一周できる |
| P2：戦闘を移植 | C#戦闘層、3人、方舟、効果予告、保存 | 既存テスト相当と代表戦闘が一致。演出省略・異なる描画速度でも結果が変わらない |
| P3：完成見本 | 完成素材3人と方舟、拠点、整備、会話、音、作戦画面 | ユーザーが出撃・指示・帰還・強化を一周し、もう一戦の理由を確認できる |
| P4：内容を増やす | 6人・3ボス・3空域へ拡張 | 新しい敵と仲間が既存の選択を変える。追加1体の制作負担が測定できている |
| P5：個人利用版の仕上げ | 手元PC向けの設定と性能調整、保存復旧、ローカル実行ファイル、バックアップ手順 | ネット接続と開発用エディターなしで起動し、最後まで遊び、終了・再開・セーブ復旧できる |

P0とP1は独立して準備できるが、P2以降の量産判断は双方の結果を見る。週数や費用は、担当人数・稼働時間・3D素材の調達方法が未定のため今は確約しない。P1で人物1人の実績、P3で完成した1戦の実績を測り、残量を見積もる。

試遊はまずユーザー本人が行い、早期発動の理由、狙った部位、再戦の動機を確認する。外部試遊は完成条件に含めない。戦闘ログは検証用にローカル保存し、外部送信しない。初回起動を含むオフライン動作、セーブのバックアップ・復旧を確認項目に加える。

## 9. 優先順位と縮小の仕方

最優先は **戦闘の判断、少女3人と巨大ボスの3D表現、短い1周の魅力**。次に装備・拠点・物語で再戦の動機を作る。

制作負担が大きければ、まず仲間数・ボス数・音声量を縮める。完成品質の人物1人が作れていない段階で、6人のモデル発注や大量の技演出を進めない。オンライン、自由飛行アクション、ミニゲーム、ランダム装備の多重厳選は後回しにする。

制作開始前に埋める情報は、制作人数と稼働、3D素材を自作・依頼・購入のどれで揃えるか、素材予算、手元のプレイ用PCと表示解像度。これらが未定でも、P0の戦闘改善とP1の素材仕様作成までは進められる。配布・販売先の検討は現在の作業に含めない。

## 10. 次の具体的な着手
