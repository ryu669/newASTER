5人編成、敵Lv1〜50、Lv45最強技、巨神獣3×8詩／人物3×6詩、敗北・撤退での聞いた詩の取得、好感度との分離、チェイン率への人物・装備補正禁止、同じ入力と種の再現性、費用・成果の一括保存を維持する。300石／3000石・★6合計3%均等・100pt専用チケットと承認済み初期97%テーブルは維持し、追加バナー等を調整名目で導入しない。既存チェイン初期値も本計画で変更対象にしない。

### 8-1：基準とデータの境界

mainのコミット、Core・Unity・プレイヤーのコードと素材bundleのハッシュ、使用定義・設定版を固定する。現行値を保存してから候補値を作り、数値変更をコード中の各画面へ分散させない。`Combat/battle-formal.json`、`Economy/kinder-trial.json`、`Economy/engagement-trial.json`とコード内の報酬／初期配布を棚卸しし、調整対象の読み込み先と責任を定める。

追加予定の試遊定義は`Resources/Trial/`配下で安定ID・schemaVersion・contentVersion・用途を持たせる。実装時に共通データ契約へ追記し、未知ID、負値、重複、参照循環、敵Lv範囲外、詩／本文不一致を読み込み前に拒否する。定義の再読込を戦闘途中や保存待ちに適用しない。

診断はtmp配下の独立saveIdと専用の保存先を必須とし、開始時・終了時に通常プレイヤー保存へ書いていないことを検査する。初期配布・貸出編成と高Lvの測定用状態は区別し、既存保存へ再配布しない。

### 8-2：一周を測る計測基盤

既存`PlaytestTelemetry`を拡張または現行保存に依存しない別の記録層へ置き換える。単調増加時計で実経過を計り、UTC日時は記録の照合に使う。sessionId／runId／battleId／操作ID／seed／入力方式／定義版／ビルドハッシュを各記録へ付ける。個人パスや他アプリ一覧は公開記録へ入れない。

| 分類 | 記録するもの |
| --- | --- |
| 時間 | 起動・ロード、入力判断、演出、画面移動、休止／非アクティブ、保存。TIME tick・演出予定秒・実経過・アクティブ時間を別単位で保存 |
| 戦闘 | 勝敗／撤退、受理／拒否入力、スキル・部位選択、破壊順、大技／最強技、被害・回復、資源不足、チェイン長と補正 |
| 収集 | 歌唱機会、聞いた詩、新規／重複、人物対応、新章、初回読了に要した戦数と時間 |
| 経済 | 開始残高、入手源・消費先・操作ID、終了残高、育成・家具・遺物・交換の到達と不足理由 |
| 生活・読書 | 家具製作・配置・使用・解除、交流、読書開始／終了／中断／回想、閉じたメニューから目的へ到達する操作数 |

イベントIDで重複を排除する。記録失敗でゲームを停止させず、当該runを「計測不完全」とする。ログ出力が乱数消費・進行・報酬へ影響しない回帰を必須にする。

### 8-3：読める試遊本文と詩対応

緑還竜3章の各8詩を本文から抽出する。5人の第1章は各6詩、計30詩を本文へ結び、緑還竜の24詩を聞いたこととの対応理由とIDを明示する。各人物の第2・3章は未制作のまま扱う。対応候補の6詩を全員同じ番号対応で生成しない。

試遊用物語はオリジナルで制作し、原作動画の文章を転載しない。解放条件を万物の書で確認でき、読了・再読・回想で報酬や好感度が重複しないことを検証する。スレイヤーのイベント1本は交流→不足理由→解放→中断／再開→読了→回想まで接続する。8章＋1イベントは量産前の制作単位であり、既存85技術sceneや正式60章の完成数に足し合わせない。

新規本文制作から実作業区間と生成・ビルド待機を分けて記録する。人物／敵の素材追加が必要なら追加単位の工数だけを記録し、計画7の過去の全制作工数へ読み替えない。1人・1敵の全制作工数は次の新規量産単位で取得する。

### 8-4：戦闘難度と攻略の調整

最初に現行値の基準を再現する。人物Lv1／10／30／60／120×敵Lv1／10／44／45／50、方策は通常攻撃中心・部位優先・15技の資源を使う攻略の3種類。方策ごとに入力列と選択ルールを固定し、小規模な試走後、同じ20 seedで25条件×3方策＝1,500戦を比較する。上限到達・敗北・撤退を除外せず結果へ含める。Lv60／120の覚醒・装備・重複は測定条件に明記し、開始から所持しているとは扱わない。

敵HP・攻撃・防御・速度・Lv曲線・部位耐久・ゲージ・行動表を主な候補とし、一度の調整で何を変えたかを残す。Lv44で最強技が出ずLv45で候補になること、角冠・左翼・右翼・尾の破壊が個別機能へ作用することを維持する。強い育成の優位を残しつつ、低Lv編成の高Lv攻略が自明にならないようにする。

初見3〜6分、既討伐周回2〜4分は既存VS-01の目標。シミュレーションの演出秒数だけで達成としない。実際の入力・判断を含む試遊時間で評価し、達しない場合は原因と採用判断を残す。Lv帯別の固定勝率や必要育成Lvは最初の測定で設定し、未測定の「Lv50まで簡単に到達」を目標にしない。

### 8-5：歌唱と章解放のテンポ

敵の行動完了で記録する歌唱機会、候補と抽選、重複取得、人物対応を計測する。歌を聞く前の討伐へ詩を補充せず、破壊で失われる機会と収集用の再戦・パスの選択を見えるようにする。既定の未取得優先案は調整候補として比較し、歌唱候補の変更と取得処理の変更を混同しない。

第1章8詩／全24詩と人物第1章6詩の初回収集まで、複数seedの実戦を継続して戦数・重複率・時間の中央値とp90を出す。打ち切り条件・未収集件数も報告する。勝利だけの実験と敗北／撤退の契約回帰を分け、章を直接解放したfixtureで収集時間を短く見せない。

### 8-6：一周の供給と費用

討伐→Lv育成→装備→家具→上位Lv→レリックハントを実際の残高で接続する。章／交流を好感度や装備強化に誤って従属させず、家具の放置で好感度を上げない。遺物の同名max統合・80%整数判定・大量消費・上限／不足時の無消費を維持する。

新規開始から最初のLv育成・装備ノード・家具・第1章・遺物強化へ届く戦数／時間、各資源の余剰と不足を測る。初期配布や討伐報酬を変える場合は試遊設定版と新規／既存保存への適用表を作る。過去の確定済みreceipt・既得資産・既読を再計算せず、ガチャ提供割合は実際の同じ定義から表示する。

Lv120の算術予算と実到達曲線を分ける。日付越えやアクティブ30分は専用時計の診断と実経過の操作確認を区別し、テストのためにOS時計を変更しない。抽選の境界・総率は決定的試験、実抽選分布はseed付きの統計記録とし、少数試行の率だけで不具合や提供率達成を断定しない。

### 8-7：保存を含む一周と回帰

新規保存、現行正式保存、正式の旧payload形からの読込を独立ケースにする。旧試遊CampaignSaveV2の移行は追加しない。討伐・読了・家具・遺物・ガチャ・交換を通して別プロセスで再起動し、残高・所持・位置・章・既読・receiptが一致することを確認する。

保存失敗・同操作再試行・二重入力・破損backup復旧・将来版拒否・別ID・内容版差を含める。新しい本文版はscriptVersionと既読／読了の適用表で管理し、fixtureの読了を新本文の読了へ自動転用しない。報酬待ち・復旧確認・未準備の操作は進行変更を停止し、原本保全と取消を維持する。

### 8-8：操作・表示・音の通し確認

本、戦闘、育成、召喚、遺物、庭、ADV、回想、設定、結果、保存待ち、復旧の操作を一覧化する。閉じる／戻る／対象変更／取消／確定と連打、パネル排他、閉じた時の不要情報、必要情報を開く導線を720p／1080pで検査する。絵を大きく見せる計画7の方針を保つ。

実操作による確認と、画面状態を直接指定する診断を分ける。文字サイズ、auto速度15／30／60／120、未読skip停止、長文・多数バックログ、CG復帰、音量保存を確認する。焦点喪失の模擬通知と実際のAltTabを区別し、復帰時の音声・タイマー・手動再開・二重再生を調べる。

PCM検査とは別に、BGMループ・5効果・音量差を実際に聴いた記録を残す。実マウス操作／AltTab／聴取を行えない実行環境では、その項目を未実施として残し、自動診断を手動受入れに置き換えない。実施可能な機能・回帰・文書化は継続する。

### 8-9：実機の性能と負荷確認

負荷測定の前に既存`tools/check-plan7-performance-environment.ps1`相当で他アプリ・CPU・GPU・空きRAMを確認する。ゲーム等が動作中、負荷過大、情報未取得なら測定用プレイヤーを起動せず延期を記録する。ユーザーの他アプリを終了しない。低負荷条件、公式CLIによる壁紙停止・finallyでの復元も既存の方式を維持する。

1080p・通常同期設定・速度1の代表通し戦闘で95%以上が16.7ms以内を確認する。720pも回帰する。初回／再読込の起動、戦闘大技・破壊、庭移動、ADV／CG／バックログの読み込み時間とピークメモリを別に測る。ロード区間・準備待ちを除いた戦闘測定と全起動時間を混ぜない。

機材、表示モード、設定、ビルドとbundle、場面、区間、フレーム数、平均・p95・p99・最大、16.7ms以内割合、外部プロセスのピークと観測間隔を保存する。画像RGBA換算をGPU実使用量と呼ばない。低性能PC、長時間、全敵に未測定の保証を付けない。冷起動は条件を明示し、OSキャッシュを強制消去せず、単にプロセスを再起動した結果と区別する。

### 8-10：完了判定と量産へ渡すもの

`plan8-progress.md`、`plan8-completion-gate.md`、試遊設定版・測定JSON・操作一覧・本文／詩／対応表・再現コマンド・画面証拠・採用／不採用理由を実装時に作る。各条件の結果をpassed／failed／not-runと実施方式・根拠へ結び付ける。

技術ゲートは実装・隔離通し操作・保存・再生一致・代表性能の成立で判定する。体験ゲートは実プレイの判断時間・導線・聴感等の記録で判定する。両方の対象条件を満たして計画8全体を完了とする。技術だけの場合は「技術ゲート完了、体験受入れ未完了」と明記し、未実施の項目を後続へ移しただけで全体を完了にしない。条件変更は理由と制作への影響を記録し、文書・試験・報告を同時に更新する。

計画9へは、1体・5人の調整済み試遊曲線、残る個体別設計、本文の採用可否、詩対応表、素材とイベントの制作数量、最終美術・聴感の残件、未測定機材、次の新規人物／敵／イベントの実工数記録を渡す。H/E/Vが揃うまでは総納期や制作費を推測値で確約しない。

既存の`validate-automatic-chain.ps1`、`compile-unity-scripts.ps1`、計画5〜6の保存／本／home検証、`validate-plan7-sample-player.ps1`、素材完了検査を必要な差分へ再利用する。計画8用のrun集約と一周を再現するスクリプトは追加予定であり、現時点で存在・合格済みとは扱わない。文書だけの変更でUnityビルド・負荷測定は行わない。

新規ブランチはfetchした最新mainから`codex/`接頭辞で作成し、PRのbaseは必ずmainにする。別の計画ブランチを親にしてマージを積み重ねない。ユーザーの未コミット設定と保存は保持する。実装と受入れを終えた単位を順次コミットし、PR説明をその最終範囲と検証結果へ合わせる。
