# ヒロイン・別衣装の追加方法

2026-10-07更新。計画10の実装で使った手順。1形態ごとに参照調査 → データと本文 → 専用画像 → 戦闘・保存検証 → Unityビルド → 実行版の画面確認を終え、その後に次の形態へ進む。

## 1. 人物と形態を先に決める

`heroine.<key>` は形態ID、`personId` は同じ人物の通常形態ID、`variantId` は `normal`・`swim`・`academy` 等。別衣装でも同じ人物なら好感度と恋人関係を共有する。Lv・スキル・神器・章とイベントの既読は形態別。同じ人物を同時に編成・庭へ重複配置しない。

新しい人物と既存人物の別衣装を混同しない。例：スレイヤー水着の `personId=heroine.slayer`。アルケイン学園の `personId=heroine.arcane`。年齢、外見、性格、口調、好きなもの、物語での成長、通常形態との連続性を `docs/references/characters/<key>.md` に残す。

## 2. 参考動画を調べる

人物・戦闘の対応する2本を確認し、プロフィール、翼・光輪・衣装・武器、スキル名・表示Lv・倍率・属性・状態効果を記録する。`tools/inspect-plan10-next-four.py` はffmpegで複数時刻を抽出し、`tmp` 内へ資料と調査シートを置く例。動画や切り出した原作画素は配布用素材へコピーしない。

観察したスキルは `ruleOrigin=video-observation-plus-newaster-original`、出典 `.mkv`・秒数・観察Lvを保持する。確認できなかったスキルを映像由来として埋めない。本作の創作なら `ruleOrigin=newaster-original`、`sourceFile=""`、`sourceSecond=0`、`observedSkillLevel=0`。アルケインの2・3番がこの例。映像のLv7の値を本作のLv1基準に採用する調整方針も人物記録へ明記する。

## 3. 戦闘カタログを1形態追加する

最新の `Resources/Combat/battle-plan10-<stage>.json` を出発点とする。過去の段階は回帰試験用に保存する。新形態は以下を揃える。

| 項目 | 契約 |
| --- | --- |
| heroine | 一意の形態ID、名前、jobId、personId、variantId、3スキル、特性、神器、章・詩・交流の参照 |
| job | 既存ジョブは再利用。新ジョブだけ追加。HP・攻撃・防御・速度・資源は本作の調整値 |
| skills | ちょうど3つ。正の待機、必要な効果・対象・属性・上限、正確な出典区分 |
| chainActions | 資源・通常WTを消費しない人物固有の固定行動。独自設定を明記 |
| contentReferences | 特性1、神器1、章3、詩リンク18、好感度イベント3、恋人イベント2を実装状態へ |

`CombatDefinitionCatalog.Validate()`、`WithFormation()`、各スキルLv1〜7の検証を行う。新しい効果は型、範囲検証、コピー／育成変換、実行、予測表示、説明をすべて接続する。全体攻撃の本体ボーナスを部位へ誤って掛けない。継続時間延長は有効な効果だけへ適用し、無効な状態を復活させない。

既存の組み立てスクリプトはその段階の再現用であり、最新内容へ過去段階を重ねるためのスクリプトではない。新しい段階のスクリプトを作り、元段階JSONから再現する。C#差し替えは対象箇所を確認し、同じ文字列が別の箇所に存在するだけで適用済みと判定しない。

## 4. 新ジョブの操作を先に通す

戦闘専用の状態は `PlayableBattle` のpartialに置き、育成保存へ持ち込まない。READY以外・戦闘不能・スタン・うわの空・資源不足・不正対象では操作を受け付けず、拒否した操作で資源や時間や乱数を進めない。

ジェネラルは本人固有の5枠プロファイルを必須にし、選択した指揮官1人の効果のみ適用する。スナイパーの通常支援は出撃前に味方1人を指定する。支援反応が別の支援反応を呼ぶ再帰を避け、資源・通常WTを維持する。ギャンブラーのSLOTは3行＋2対角の5ラインを全部評価し、重複ラインと777の全発動を省略しない。全外れだけWT0。数値と待機は本作の調整値として記録する。

ジョブ資源画像は `Resources/UI/Jobs/<job>.png`。`tools/author-job-resource-icons.py` は既存のコード由来の図形アイコンを拡張する作例。色以外に形そのものを分ける。新しいジョブを増やす時は戦闘の操作・リソース説明・人物の特性説明・編成の役割表示まで追加する。

## 5. 本文と人物記録を作る

1形態に3章・各10ページ、18詩、好感度3イベント＋恋人2イベント・各8段落を作る。3章は巨神獣の詩の実在IDへ結び、対応理由を保存する。`tools/author-plan10-arcane-story.py` は本文の作例。物語JSON、Unity用累積JSON、人が読む `docs/story-text` の本文を同時に出力する。

既存形態を改名しただけの本文にしない。人物の欲求と口調、参照した巨神獣の記録、主人公との選択を繋ぐ。衣装違いでも人格や恋人関係をリセットせず、同じ人物の別の経験を描く。ゲームの分岐説明や「既に恋人の場合は」といった制作上の注記を作中の地の文へ入れない。

段階JSONは元の章・イベントへ新形態分を追加する。`ProductionStoryContent.Validate()`、UnityのJsonUtility往復で30ページが保たれること、実際の読了・保存・再読・好感度共有を検証する。

## 6. 専用画像18点を作る

立ち絵を最初に制作・確認し、同じ成人の顔・髪・衣装・翼・光輪を基準に以下を制作する。

| 用途 | キー |
| --- | --- |
| 人物 | standing、portrait、expression-joy、expression-puzzled、expression-determined |
| 戦闘 | attack、hit、cutin |
| 庭 | sd-idle、sd-walk、sd-talk、sd-react |
| 神器 | equipment-tree-v1 |
| 交流 | event-0-cg〜event-4-cg |

CG以外は実際の透明背景、CGは場面全体の画像。顔・手・武器・翼、帽子や光輪の欠け、人物の重複、キャンバス外への切れを見て確認する。立ち絵・表情・戦闘・SDは全身と翼を収め、余白を取る。専用画像が揃うまで既存人物の絵を流用しない。

生成・修正はImageGenを使う。生成PNGをローカルの画像処理で加工せず、修正が必要ならImageGenで再生成する。`game/art-source/plan10/<key>-generation.json` に画像ごとのプロンプトと生成元を残し、`tools/adopt-plan10-form-art.py <key>` で元PNGを無加工コピーする。採用後はResourcesとart-sourceのSHA-256一致、透明画像のalpha、18種類の揃いを検証する。生成元の絶対パスは制作履歴であり、新しい環境では保存済みのart-source PNGを使う。

新しい `.meta` のGUIDを再利用しない。Unityでalpha・Texture2D・mipmap無効・サイズ上限・圧縮条件を確認する。参考映像と `tmp` の調査画像はGit・配布物へ含めない。

### 誓女選択用の肖像を揃える

一覧・詳細・編成の人物表示は、顔を基準にした上半身の共通画角を使う。横長肖像、縦長肖像、全身絵を同じ枠へ単純にScaleToFitして混在させない。人物の顔中心を枠の横50%・縦40%、顔の高さを枠の18%へ合わせる。元画像の縦横比を維持し、枠外はクリップする。上半身表示では翼の外縁や脚が枠外になることは許容するが、顔・髪の上端が切れないことを確認する。

`Resources/UI/heroine-portrait-framing.json` に、形態ごとに以下を登録する。同じ人物の衣装違いも画像ごとに測る。

| フィールド | 登録内容 |
| --- | --- |
| heroineId | 戦闘カタログと一致する形態ID |
| resourcePath | 本人のportraitまたはstanding画像。拡張子なしのResources相対パス |
| faceCenterX / faceCenterY | 元画像の左上原点・0〜1の顔中心。光輪、帽子、翼を含めない |
| faceHeight | 元画像の全高に対する、額から顎までの顔の高さ。髪飾りを含めない |

枠へ合わせるためのPNGの引き伸ばしや切り出しは不要。表示は `DrawHeroPortrait` に集約し、人物ごとの画面座標や個別の拡大処理を追加しない。画像を再採用したら顔基準も再測定する。原画の顔・衣装などの修正が必要な場合はImageGenを使用する。

顔だけに寄った肖像は、顔のサイズを揃えると画像の下端が枠の途中で終わることがある。この場合は、本人のstanding画像を同じ顔基準で上半身表示する。現在のRがこの例。今後のportrait制作では胸から腰までの描画を用意し、顔の上だけでなく下にも画角調整の余裕を残す。

採用前に一覧の全ページ、本人詳細、編成候補で比較する。顔の大きさ、目線の高さ、上半身の見え方、左右の中心、クリップ範囲を揃える。新形態の定義漏れや画像の読み込み失敗を、星の代替表示のまま完成扱いにしない。

## 7. 戦闘・人物・神器・庭へ接続する

`Illustrations/<key>-battle-binding.json` に形態IDとstanding/attack/hit/cutinを登録する。戦闘バインドはJSONを自動列挙するため、人物IDの追加リストをC#へ書く必要はない。人物表示の専用HomeArtを `ProductionStoryCatalog.Home` へ接続し、採用ハッシュを `ProductionAssetAcceptance` へ登録する。

神器は既存の `WeaponOwners` の末尾へ追記し、旧インデックスをずらさない。3枝の名前・係数・最終特性の意匠を追加する。人物配列の順序が変わっても既存神器の性能が変わらないようにする。拡張人物は通常攻撃の名称・威力を神器で上書きせず、対象の攻撃スキルに神器倍率を掛ける。

人物の特性名と熟達特性、ジョブ名・説明を `HeroineIdentityCatalog` と `HeroineTraitRules` へ追加する。庭SDのリソース名は専用キーで読み込む。加入は初期5人以外の形態をカタログから列挙し、5形態ごとにページを分ける。

## 8. 編成の階層と装備枠を維持する

編成は「5人の配置 → 隊員の設定 → 入れ替え候補」。隊員設定へ神器1枠、オーパーツ1枠の場所、護衛対象、指揮官、スナイパー支援、パンツァー設定を置く。神器画面から戻ると元の隊員設定へ戻す。Escapeも階層を一つずつ戻る。

オーパーツは今回、1人1枠の表示場所を準備した。装備操作・個別オーパーツの能力適用・新しい装備保存形式は後続実装。既存の遺物収集による能力と混同せず、未実装の装備を使えるように見せない。衣装間で装備を共有するかの詳細は、後続実装時に確定する。

指揮官・支援対象の変更はHomeOperationの原子保存で扱い、保存失敗なら同じリクエストで再試行する。取消で消費しない。既存保存に新フィールドが無い時は自動選択・既定値で読み込む。未所有の人物や不正なジョブへ指定できない。

## 9. 画面比率と位置を検証する

UIは論理1600×900の比率を保ち、違う比率のウィンドウでは余白を置く。画像を `StretchToFill` で人物や木へ押し込まない。人物・CGは `ScaleToFit`、背景と同一キャンバスの背景レイヤーは同じ `ScaleAndCrop` で描く。切り抜き領域を使う場合もその領域の縦横比を保つ。

神器の装飾画像は比率を保持し、操作ノードの図は中央の読みやすい幅で配置する。ノードの名前やLvが重ならず、描画位置とボタンの当たり判定が一致することを確認する。CGは本文に隠れない表示領域へ収める。

最低限、加入、一覧の全ページ、詳細、スキル強化、神器、編成3階層、戦闘・固有操作・状態、庭・交流、3章、5イベント、読了保存を確認する。現在の表示確認はユーザー指定により最大サイズの1600×900のみで実行する。絵の頭・翼・足、文字の切れ、操作を遮る表示、戻る経路も見る。上半身表示の意図したクリップと、全身素材の欠けは区別する。

## 10. 検証と記録を揃える

`tools/validate-automatic-chain.ps1` はCore/Dataの単体・保存・回帰試験。新しい効果には予測と実ダメージ、対象別の倍率、資源と時間の原子性、反応の非再帰、状態の期限、旧保存の互換を検証する。`tools/compile-unity-scripts.ps1` はUnity用C#をコンパイルする。

Editorの段階別Buildは18画像のハッシュ、戦闘・物語・Home参照、Unity JSON往復、Windowsビルドを検証する。Playerの段階別スクリプトは別保存で画面を開き、成功ログと非黒画像を確認する。キャプチャ時は可視ウィンドウで起動し、制作時のバックグラウンドUnityはHiddenで起動する。`tools/record-plan10-form-acceptance.py <key>` は実在する成功ログと採用PNGだけを記録する。

現行ロットの再検証は `tools/validate-plan10-expanded-roster.ps1`。必要な段階別フラグをまとめて設定し、終了時に元の環境へ戻す。最新のUnityビルドは `Plan10ShangrilaBuild.ValidateAndBuild`、本人の実行画面は `tools/validate-plan10-shangrila-player.ps1`、全体UIは `tools/validate-plan10-ui-player.ps1`。撮影と同じ出力先の再ビルドを同時に走らせない。

別PCで生成元パスが存在しない場合、採用ツールは保存済みの `game/art-source/plan10/<key>` へ戻る。`--saved-source` を付けてこの経路を指定できる。再生成は最初に採用画像を確認し、ImageGenで行う。

新しい保存操作を足す場合、操作の検証だけでなく、保存ジャーナルの要求種別一覧も更新する。隊長・支援対象の変更は保存失敗、再試行、重複要求、旧保存の既定値まで確認する。人数が増える一覧はページ分けかスクロール領域へ収め、最後の人物の選択画面も確認する。

最後に人物記録・本文・実装記録・素材と検証JSON、計画10の名簿、README、文書索引、担当のsystems/data/presentationを更新する。履歴の文書まで現行数量に書き換えない。GitHubへの反映は検証済みのソース・画像・資料をコミットし、実行ファイル・元動画・調査画像・無関係なUnity変更を含めない。
