# ヒロイン・別衣装の追加方法

2026-10-09更新。Plan11-9／Plan12向けの制作手順。1形態ごとに参照調査 → データと本文 → 専用画像 → 戦闘・保存検証 → Unityビルド → 実行版の画面確認を終え、その後に次の形態へ進む。

## 1. 人物と形態を先に決める

`heroine.<key>` は形態ID、`personId` は同じ人物の通常形態ID、`variantId` は `normal`・`swim`・`academy` 等。別衣装でも同じ人物なら好感度と恋人関係を共有する。Lv・スキル・神器・章とイベントの既読は形態別。同じ人物を同時に編成・庭へ重複配置しない。

新しい人物と既存人物の別衣装を混同しない。例：スレイヤー水着の `personId=heroine.slayer`。アルケイン学園の `personId=heroine.arcane`。年齢、外見、性格、口調、好きなもの、物語での成長、通常形態との連続性を `docs/references/characters/<key>.md` に残す。

## 2. 参考動画を調べる

人物・戦闘の対応する2本を確認し、プロフィール、翼・光輪・衣装・武器、スキル名・表示Lv・倍率・属性・状態効果を記録する。`tools/inspect-plan10-next-four.py` はffmpegで複数時刻を抽出し、`tmp` 内へ資料と調査シートを置く例。動画や切り出した原作画素は配布用素材へコピーしない。

観察したスキルは `ruleOrigin=video-observation-plus-newaster-original`、出典 `.mkv`・秒数・観察Lvを保持する。確認できなかったスキルを映像由来として埋めない。本作の創作なら `ruleOrigin=newaster-original`、`sourceFile=""`、`sourceSecond=0`、`observedSkillLevel=0`。アルケインの2・3番がこの例。映像のLv7の値を本作のLv1基準に採用する調整方針も人物記録へ明記する。

## 3. 戦闘カタログを1形態追加する

現行の `Resources/Combat/battle-plan11-7.json` を出発点とする。過去の段階は回帰試験用に保存する。新形態は以下を揃える。

| 項目 | 契約 |
| --- | --- |
| heroine | 一意の形態ID、名前、jobId、personId、variantId、3スキル、特性、神器、章・詩・交流の参照 |
| job | 既存ジョブは再利用。新ジョブだけ追加。HP・攻撃・防御・速度・資源は本作の調整値 |
| skills | ちょうど3つ。正の待機、必要な効果・対象・属性・上限、正確な出典区分 |
| chainActions | 資源・通常WTを消費しない人物固有の固定行動。独自設定を明記 |
| contentReferences | ジョブ特性2＋キャラ特性3＋交流特性3（標準合計8）、神器1、章3、詩リンク18、可変数のイベントを実装状態へ |

`CombatDefinitionCatalog.Validate()`、`WithFormation()`、各スキルLv1〜7の検証を行う。新しい効果は型、範囲検証、コピー／育成変換、実行、予測表示、説明をすべて接続する。全体攻撃の本体ボーナスを部位へ誤って掛けない。継続時間延長は有効な効果だけへ適用し、無効な状態を復活させない。

既存の組み立てスクリプトはその段階の再現用であり、最新内容へ過去段階を重ねるためのスクリプトではない。新しい段階のスクリプトを作り、元段階JSONから再現する。C#差し替えは対象箇所を確認し、同じ文字列が別の箇所に存在するだけで適用済みと判定しない。

## 4. 新ジョブの操作を先に通す

戦闘専用の状態は `PlayableBattle` のpartialに置き、育成保存へ持ち込まない。READY以外・戦闘不能・スタン・うわの空・資源不足・不正対象では操作を受け付けず、拒否した操作で資源や時間や乱数を進めない。

ジェネラルは本人固有の5枠プロファイルを必須にし、選択した指揮官1人の効果のみ適用する。スナイパーの通常支援は出撃前に味方1人を指定する。支援反応が別の支援反応を呼ぶ再帰を避け、資源・通常WTを維持する。ギャンブラーのSLOTは3行＋2対角の5ラインを全部評価し、重複ラインと777の全発動を省略しない。全外れだけWT0。数値と待機は本作の調整値として記録する。

ジョブ資源画像は `Resources/UI/Jobs/<job>.png`。`tools/author-job-resource-icons.py` は既存のコード由来の図形アイコンを拡張する作例。色以外に形そのものを分ける。新しいジョブを増やす時は戦闘の操作・リソース説明・人物の特性説明・編成の役割表示まで追加する。

## 5. 本文と人物記録を作る

1形態に3章・各10ページ、18詩を作る。好感度は基本3イベント＋恋人2イベント、専用画像18点を標準目標とする。イベント・回想数は可変で、短い本文やCGなしの追加も可能。3章は巨神獣の詩の実在IDへ結び、対応理由を保存する。`tools/author-plan10-arcane-story.py` は本文の作例。物語JSON、Unity用累積JSON、人が読む `docs/story-text` の本文を同時に出力する。

既存形態を改名しただけの本文にしない。人物の欲求と口調、参照した巨神獣の記録、主人公との選択を繋ぐ。衣装違いでも人格や恋人関係をリセットせず、同じ人物の別の経験を描く。ゲームの分岐説明や「既に恋人の場合は」といった制作上の注記を作中の地の文へ入れない。

段階JSONは元の章・イベントへ新形態分を追加する。`ProductionStoryContent.Validate()`、UnityのJsonUtility往復で30ページが保たれること、実際の読了・保存・再読・好感度共有を検証する。

## 6. 専用画像18点を作る

立ち絵を最初に制作・確認し、同じ成人の顔・髪・衣装・翼・光輪を基準に以下を制作する。

| 用途 | キー |
| --- | --- |
| 人物 | standing、portrait、expression-joy、expression-puzzled、expression-determined |
| 戦闘 | attack、hit、cutin |
| 庭 | sd-idle、sd-walk、sd-talk、sd-react |
| 神器 | equipment-tree-v1 |
| 交流 | event-0-cg〜event-4-cg |

CG以外は実際の透明背景、CGは場面全体の画像。顔・手・武器・翼、帽子や光輪の欠け、人物の重複、キャンバス外への切れを見て確認する。立ち絵・表情・戦闘・SDは全身と翼を収め、余白を取る。専用画像が揃うまで既存人物の絵を流用しない。

生成・修正はImageGenを使う。生成PNGをローカルの画像処理で加工せず、修正が必要ならImageGenで再生成する。`game/art-source/plan10/<key>-generation.json` に画像ごとのプロンプトと生成元を残し、`tools/adopt-plan10-form-art.py <key>` で元PNGを無加工コピーする。採用後はResourcesとart-sourceのSHA-256一致、透明画像のalpha、18種類の揃いを検証する。生成元の絶対パスは制作履歴であり、新しい環境では保存済みのart-source PNGを使う。

新しい `.meta` のGUIDを再利用しない。Unityでalpha・Texture2D・mipmap無効・サイズ上限・圧縮条件を確認する。参考映像と `tmp` の調査画像はGit・配布物へ含めない。

### 誓女選択用の肖像を揃える

一覧・詳細・編成の人物表示は、アイコノクラスト・アンダーマイン・エキドナのような横長の上半身肖像を基準にする。今後の追加ヒロインと衣装違いにも同じ基準を適用する。portraitは立ち絵とは別に、ネイティブ1536×1024以上・3:2・RGBA PNGで制作する。全身絵の拡大切り抜きや低解像度絵の拡大書き出しで代用しない。額から顎まで128画素以上を確保し、頭・両肩・胸から腰までを描く。顔の上と下に画角調整の余裕を残す。

人物の顔中心を表示枠の横50%・縦40%、顔の高さを枠の18%へ合わせる。元画像の縦横比を維持し、枠外はクリップする。選択後の詳細画面も同じ肖像を使い、ネイティブ画素を超える拡大は行わない。上半身表示では翼の外縁や脚が枠外になることは許容するが、顔・髪の上端が切れないことを確認する。

`Resources/UI/heroine-portrait-framing.json` に、形態ごとに以下を登録する。同じ人物の衣装違いも画像ごとに測る。

| フィールド | 登録内容 |
| --- | --- |
| heroineId | 戦闘カタログと一致する形態ID |
| resourcePath | 本人の専用横長portrait画像。拡張子なしのResources相対パス |
| faceCenterX / faceCenterY | 元画像の左上原点・0〜1の顔中心。光輪、帽子、翼を含めない |
| faceHeight | 元画像の全高に対する、額から顎までの顔の高さ。髪飾りを含めない |

枠へ合わせるためのPNGの引き伸ばしや切り出しは不要。表示は `DrawHeroPortrait` に集約し、人物ごとの画面座標や個別の拡大処理を追加しない。画像を再採用したら顔基準も再測定する。原画の顔・衣装などの修正が必要な場合はImageGenを使用する。

顔だけに寄った肖像や縦長の全身絵は、ImageGenで本人の顔・髪・衣装・翼・光輪を保った横長の上半身肖像へ作り直す。R、アナイアレイター、アナイアレイター（聖夜）、オリフラム、シェルの修正例と実際のプロンプトは `game/art-source/heroine-portraits-v2/generation.json`。生成元PNGとResourcesは無加工コピーし、SHA-256を `ProductionAssetAcceptance.Hashes` へ登録する。

Unityは `HeroinePortraitImporter` がRGBA32・無圧縮・mipmap無効・NPOT変換なし・Clamp・最大4096へ統一する。`HeroinePortraitBuildValidation` がすべてのPlayerビルド前に、登録漏れ、ネイティブ寸法、3:2、顔の画素数、透明背景、顔の不透明度、採用ハッシュ、取り込み後の画素保持を検証する。新規ヒロインは基準違反でビルドを失敗させる。schemaVersionは2。

実装済み全15人を同じ基準へ移行済み。`legacyPortrait` の例外は廃止し、既存人物・衣装違い・今後の追加人物をすべて同じビルド検査へ通す。一覧・詳細・編成・育成・召喚は共通の `DrawHeroPortrait` を使用する。ナイトホーク、水着スレイヤー、アルケイン、学園アルケイン、シャングリラの新素材と生成プロンプトは `game/art-source/heroine-portraits-v2/all-implemented-generation.json` に記録する。

万物の書のページ移動は上部の画像しおりへ集約する。縦長のしおりを使い、選択中だけ左側に移動して名称を縦書きで表示する。非選択のしおりはページごとの固定位置を保ち、文字を出さない。説明文は右上の「？」から表示する。通常画面にクリック方法・Escなどの操作説明を置かない。ページ固有の内容、能力値、費用、解放条件は表示する。

誓女のスキル・特性と書のしおりは `Resources/UI/book-emblems-v1` の画像アトラスを使用する。ジョブ固有資源には `Resources/UI/Jobs` の専用画像を使う。今後の新しいアイコンも画像リソースとして登録し、文字記号で代用しない。神器の木はヒロイン専用の `Illustrations/heroine-weapon-tree-<key>-v1` 画像を制作し、`UI/heroine-weapon-trees.json` に全13ノードの枝上座標を登録する。画像とノードは同じ表示矩形・縦横比を使用する。ネイティブ1536×1024のRGBA原本を拡大せず、人物の衣装・武器・色・装飾を加えながら幹・根・枝のある木として描く。木の幹・根・枝・葉が見えること、13ノードが枝の上に載ること、隣のノードと選択領域が重ならないことを1920×1080で確認する。人物別の枝の座標・葉の色を変更してよい。

採用前に一覧の全ページ、本人詳細、編成候補で比較する。顔の大きさ、目線の高さ、上半身の見え方、左右の中心、クリップ範囲を揃える。新形態の定義漏れや画像の読み込み失敗を、星の代替表示のまま完成扱いにしない。

本人の詳細撮影は `tools/validate-plan10-ui-player.ps1 -Views detail -HeroineId heroine.<key> -PlayerPath <最新Playerの相対パス>`。一覧の全ページと編成候補も撮影する。1600×900の実表示でアイコノクラスト・アンダーマイン・エキドナと比較し、拡大画面の顔・衣装の細部が同程度に読めることを確認する。採用ハッシュと、実際に成功した画像・ログを検証記録へ残す。

## 7. 戦闘・人物・神器・庭へ接続する

`Illustrations/<key>-battle-binding.json` に形態IDとstanding/attack/hit/cutinを登録する。戦闘バインドはJSONを自動列挙するため、人物IDの追加リストをC#へ書く必要はない。人物表示の専用HomeArtを `ProductionStoryCatalog.Home` へ接続し、採用ハッシュを `ProductionAssetAcceptance` へ登録する。

神器は既存の `WeaponOwners` の末尾へ追記し、旧インデックスをずらさない。3枝の名前・係数・最終特性の意匠を追加する。人物配列の順序が変わっても既存神器の性能が変わらないようにする。拡張人物は通常攻撃の名称・威力を神器で上書きせず、対象の攻撃スキルに神器倍率を掛ける。

人物の特性名と熟達特性、ジョブ名・説明を `HeroineIdentityCatalog` と `HeroineTraitRules` へ追加する。庭SDのリソース名は専用キーで読み込む。加入は初期5人以外の形態をカタログから列挙し、5形態ごとにページを分ける。

## 8. 編成の階層と装備枠を維持する

編成は「5人の配置 → 隊員の設定 → 入れ替え候補」。隊員設定へ神器1枠、オーパーツ1枠の場所、護衛対象、指揮官、スナイパー支援、パンツァー設定を置く。神器画面から戻ると元の隊員設定へ戻す。Escapeも階層を一つずつ戻る。

オーパーツは1形態1枠へ装備する。職印13種と独立した特殊品5種を用意し、ジョブ一致、単能力強化、ターンごとの増減を個別に加算する。既存の遺物収集効果と装備効果を重複適用しない。加入形態にも装備と保存の検証を適用する。

指揮官・支援対象の変更はHomeOperationの原子保存で扱い、保存失敗なら同じリクエストで再試行する。取消で消費しない。既存保存に新フィールドが無い時は自動選択・既定値で読み込む。未所有の人物や不正なジョブへ指定できない。

## 9. 画面比率と位置を検証する

UIは論理1600×900の比率を保ち、違う比率のウィンドウでは余白を置く。画像を `StretchToFill` で人物や木へ押し込まない。人物・CGは `ScaleToFit`、背景と同一キャンバスの背景レイヤーは同じ `ScaleAndCrop` で描く。切り抜き領域を使う場合もその領域の縦横比を保つ。

神器の装飾画像は比率を保持し、操作ノードの図は中央の読みやすい幅で配置する。ノードの名前やLvが重ならず、描画位置とボタンの当たり判定が一致することを確認する。CGは本文に隠れない表示領域へ収める。

最低限、加入、一覧の全ページ、詳細、スキル強化、神器、編成3階層、戦闘・固有操作・状態、庭・交流、3章、5イベント、読了保存を確認する。論理解像度1600×900、最終確認1920×1080に加えて1280×720でも崩れを検証する。絵の頭・翼・足、文字の切れ、操作を遮る表示、戻る経路も見る。上半身表示の意図したクリップと、全身素材の欠けは区別する。

## 10. 検証と記録を揃える

`tools/validate-automatic-chain.ps1` はCore/Dataの単体・保存・回帰試験。新しい効果には予測と実ダメージ、対象別の倍率、資源と時間の原子性、反応の非再帰、状態の期限、旧保存の互換を検証する。`tools/compile-unity-scripts.ps1` はUnity用C#をコンパイルする。

Editorの段階別Buildは18画像のハッシュ、戦闘・物語・Home参照、Unity JSON往復、Windowsビルドを検証する。Playerの段階別スクリプトは別保存で画面を開き、成功ログと非黒画像を確認する。キャプチャ時は可視ウィンドウで起動し、制作時のバックグラウンドUnityはHiddenで起動する。`tools/record-plan10-form-acceptance.py <key>` は実在する成功ログと採用PNGだけを記録する。

現行ロットの再検証は `tools/validate-plan10-expanded-roster.ps1`。必要な段階別フラグをまとめて設定し、終了時に元の環境へ戻す。最新のUnityビルドは `Plan119BuildValidation.Build`（`-buildOutput ../Builds/plan11-9/newASTER.exe`）、本人の実行画面は `tools/validate-plan10-shangrila-player.ps1`、全体UIは `tools/validate-plan10-ui-player.ps1`。撮影と同じ出力先の再ビルドを同時に走らせない。

別PCで生成元パスが存在しない場合、採用ツールは保存済みの `game/art-source/plan10/<key>` へ戻る。`--saved-source` を付けてこの経路を指定できる。再生成は最初に採用画像を確認し、ImageGenで行う。

新しい保存操作を足す場合、操作の検証だけでなく、保存ジャーナルの要求種別一覧も更新する。隊長・支援対象の変更は保存失敗、再試行、重複要求、旧保存の既定値まで確認する。人数が増える一覧はページ分けかスクロール領域へ収め、最後の人物の選択画面も確認する。

最後に人物記録・本文・実装記録・素材と検証JSON、計画10の名簿、README、文書索引、担当のsystems/data/presentationを更新する。履歴の文書まで現行数量に書き換えない。GitHubへの反映は検証済みのソース・画像・資料をコミットし、実行ファイル・元動画・調査画像・無関係なUnity変更を含めない。


神器の3枝は攻撃（攻撃・技倍率・与ダメージ）、守護（両防御・軽減、ヒーラーは回復）、技巧（速度・会心威力・資源獲得）で役割を分ける。同じ枝の固有能力の種類を4段階で維持し、先のノードほど効果を強くする。次ノードLv1が前ノードLv7の通常能力を下回らず、攻撃・技倍率・固有能力は上回ることを自動検証する。各枝の段階ごとに通常能力の種類を増やし、会心・魔防・速度・会心威力・能力割合補正を段階的に解放する。各ノードの固有能力は一つとし、装備したノードの能力が発動する。表示アイコンは通常能力の一覧から生成せず、WeaponGrowthRules.Icon と Resources/UI/weapon-effects-v1 から固有能力に対応する画像を一つだけ使用する。見た目だけの効果追加や、実際の効果と異なる記号を禁止する。


## 11. 箱庭の共通生活へ接続する

新しい形態は所持名簿から共通生活AIへ自動参加する。同一人物の衣装違いは `personLinks` を登録し、庭で二重に表示しない。人物固有の好みや台詞を共通AIへ仮入力しない。任意の `GardenBehaviorProfile` を追加する場合も、専用仕様がある行動比重・タグだけを設定する。

庭SDは本人の基本 `idle` を必須とし、専用 `sit/work/look` は任意で同じ表示基準へ揃える。専用動作が無い場合は本人の共通姿勢・静止画へ戻し、別人物のSDへ置き換えない。共通入浴は本人SDの下半身を水面で隠す。立ち絵の統一基準と神器の画像・ノード効果は、以降の形態にも適用する。

生活AIから好感度・恋人・誓い・戦闘能力・物語既読を変更しない。庭の「話す」は短い反応、「観察」はシステム描写、既存交流物語は明示した入口からADVを開く。Plan11-3の関係システムの既存イベントIDを維持する。

`Plan12GardenLifeTests` と最新Windows Playerで、表示中8人以内、形態重複なし、本人SDの動作、家具利用、Social、庭移動・ADVからの復帰、保存失敗の再試行を確認する。最新Windowsビルドは `Plan12Build.Build`。


## 12. Plan11-3の好感度・恋愛

好感度は人物IDごとのLv／EXPを参照し、形態独自の好感度や恋人フラグを追加しない。初期Lvは必要な人物だけ `initialAffections` に登録する。衣装追加時は同じ `personId` を維持し、旧数値・既読を引き継ぐ。

イベントは人数×5件という固定数を前提にしない。`ProductionStoryContent.events` に本文とscript用の元データを追加し、必要に応じて `affectionEvents` に `HeroineEventDef` を登録する。id・personId・任意のformId・requiredAffectionLevel・category・scriptId・visibility・displayOrderを指定する。形態を限定しない場合はformIdを省略する。基本イベントはLv0〜20に配置し、他イベントの既読を解放条件にしない。Lv21以降の任意の回想は報酬も必須の進行条件も持たせない。短いイベントやCGなしのイベントも登録できる。

会話を追加するときは内容IDを安定させる。同じボタンから別の会話が成立した場合はその会話IDを報酬イベントへ渡す。キャンセル・失敗・観察では付与せず、完了後だけ共通の `AffectionRewardService` を使う。回想は必ずReplayで開き、EXP・財布・既読を変更しない。

人物追加後にAF-01〜AF-14、衣装共有、イベント動的列挙、未読数とvisible／hint／hiddenを確認する。指輪と上限99のUIは共通の `AffectionView` を利用する。


## Plan11-4の装備・効果へ接続する

追加人物の編成枠は、人物を入れ替えても同じオーパーツを保持する。衣装共有の好感度とは別に、装備は枠IDで扱い、人物固有のオーパーツ所持数や装備保存を増設しない。プレビュー・戦闘は `OopartDef` の5能力固定加算と独立条件判定を共通経路で使用する。

新しいオーパーツ定義は `ProductionOopartCatalog` に5項目のLv成長・抽選上限・0～2効果・直接強化の高Lv素材を設定する。同種の行動不能付与強化は原則1種類まで。耐性無視・確定付与は追加しない。ジョブ・スキル・行動などの条件はAND/ORを明示し、画面でも各効果の条件不一致と戦闘中判定を表示する。

味方バフは実際の発動者・発動元IDを保持する共通バフ経路に接続し、受け手のバフ強化を参照しない。持続時間を延長する新しいヒロインスキルは設けず、パンツァーツールの共通延長に従う。敵の状態異常延長とは区別する。歌唱中の全ゲージ取得禁止とアーマー復帰時のツール非回復を維持する。

追加時は旧セーブ互換、人物入替・空枠保持、実能力比較、装備だけの局所補正、条件判定、バフ発動者、保存失敗再試行を[Plan11-4検証](plan11-4-ooparts.md)へ追加する。

## 編成画面の共通ルール

部隊は誓女ページから独立した「編成」のしおりで操作する。追加人物にも、画像カード直下のオーパーツ枠、左詳細・右候補4列×2段の入れ替え、候補選択と「決定」の分離を適用する。現在の編成一覧や操作説明を入れ替え画面に再掲しない。固有ジョブの設定はカードのメニューへ、操作説明は現在画面の「？」へ集約する。

表示確認は最大サイズ1920×1080で行い、誓女・オーパーツの入れ替えと保存後の復帰、枠装備の保持も確認する。画面仕様は [編成・入れ替え画面](formation-ui.md) を参照。

## 召喚対象への反映

召喚対象は衣装違いを含む実装済みの全ヒロイン形態。初期編成や現在の編成、未所持一覧で絞り込まない。本番バナーは `CombatDefinitionCatalog.HeroineIds` から生成し、全形態の石抽選・指名チケット交換・チケット使用を検証する。★6合計3%を全対象で均等配分し、対象数・各形態の割合・一覧ページ数を実データから表示する。現在は15形態・各0.2%。人物追加後も全形態の到達性と既存チケット・所持・報酬履歴の保存を確認する。

## 人物特性と神器ノード

人物の特性はジョブ特性2・キャラ特性3・交流特性3の計8件を標準とする。第1枠はジョブマスタリー、第2枠は人物制作時に選んだジョブ候補から固定し、第3～5枠にキャラ特性、第6～8枠に交流特性を配置する。ジョブ操作説明を特性として数えない。ジョブ特性は `CombatTraitCatalog` の13マスタリー＋17第2候補を再利用する。27種類は `InteractionTraitCatalog` の交流特性であり、数値効果や重複Rankによる成長を持たない。`HeroineIdentityCatalog.Traits` と戦闘側の定義を一致させ、固有効果は `HeroinePersonalAbility`、熟達は `HeroineTraitRules.MasteryBonusForHero` へ登録する。8件を超える定義を表示側で切り捨ててはいけない。

根以外の神器ノードには通常能力と固有能力を1種類ずつ定義し、`uniqueAbilityKind` と `uniqueAbilityPercent` を設定する。ノードは `WeaponGrowthRules.Icon` で決まるアイコン1つだけを表示する。根は固有能力・Lvなしで、加入時から解放・装備済み。既存の枝装備は初期化で上書きしない。

追加ヒロインと衣装違いは、初期5人以外を含む編成でも戦闘を開始できることを確認する。詳しくは [人物特性・神器ノード・戦闘開始](heroine-abilities-and-battle-start.md) を参照。共通のUIアイコンは既存画像を再利用できる。本人画像を別人物から流用してはいけない。


## Plan11-9／Plan12の追加・受入れ手順

用語は「交流特性」（27種類）と「ジョブ特性」（戦闘の固定第1・第2枠）へ統一する。人物IDは `personId`、形態IDは `id`。旧通常形態でpersonIdが省略されている場合は `CombatDefinitionCatalog.PersonId` が自身へ解決するため、既存セーブのIDを変更しない。

ジョブ特性の効果はキャラ重複Rankから `CombatTraitCatalog.Rank` で解決する。交流特性は表示用 `interactionTraitIds` と日常判定のみの `profileTraitIds` を区別し、反応スタイルはメイン1＋任意サブ1。人物の標準は `DailyReactionProfiles.For(personId)`、形態指定は `reactionStyleMain/Sub`。新人物の標準プロフィールの登録漏れも一括検証で検出する。

好感度は人物単位Lv0～99。通常上限20、指輪で99へ解放する。形態単位の育成・物語既読と混同しない。イベント数を人数×5で固定しない。オーパーツは編成枠装備であり人物入替後も枠に残る。

セーブは2スロット、各2世代バックアップ。保存・復元・削除は既存 `SaveSlotManager`／トランザクションを通す。追加データにより既存IDの意味を変更せず、新定義追加後の既存セーブ読込と二重消費防止を確認する。画面選択を保存完了で閉じたりリセットしたりしない。

1形態ずつ、人物・形態 → 戦闘・特性・神器 → 物語・交流 → 専用画像 → 自動テスト → Unityビルド → Player画面 → 制作記録・コミットまで完了する。5形態ごとに全体回帰・画風・特性分布をレビューする。

`HeroineProductionValidation.Errors` は現行カタログについて人物・形態参照、3スキル、特性8枠・順序・重複Rank、反応スタイル、3章30ページ18詩、イベント本文、肖像・神器13ノードを再利用した検証へ接続し、対象ID・項目・原因を返す。`Plan119BuildValidation` がビルド前に実行する。画像原本・SHA-256・透過・肖像寸法は既存 `HeroinePortraitBuildValidation` と人物別素材検証を引き続き通す。

検証入口は `tools/validate-plan11-9.ps1`。ダミーはテスト内のみ、製品カタログへ保存しない。肖像の保持は最大24、神器画像は最大3、戦闘レイヤーは表示単位36、SD画像は48、ADV画像は24、表情合成RenderTextureは12、庭の合成画像は前後24組とし、必要時読込・使用頻度による解放を共通表示経路へ適用する。表情合成の破棄はキャッシュの所有権に従い、差替え・退避・画面終了で重複破棄しない。欠落画像は別人物で埋めない。人物一覧の肖像は最大12件の表示待ちキューから1フレーム最大2枚、処理時間4msを目安に分割して読み込む（1枚の読込自体は途中中断できない）。ページ変更後に不要となった要求は破棄し、読み込み中は汎用アイコンを表示する。初回表示の計測は肖像が揃った描画までを含める。

Critical（セーブ消失・進行不能・二重消費）とHigh（特性不発・操作不能・人物画像違い）が残る場合は量産開始を保留し、未解決課題へ記録する。数値バランスの最終調整はPlan11-10。

量産前の画像負荷検証には `Plan119LoadFixtureBuild.BuildAndPlayer` を使用する。1536×1024の異なる合成画像320枚を別のAssetBundleへ出力し、生成したAssetsを削除してから製品をビルドする。生成フォルダが残っている場合は製品ビルドを拒否する。原画や人物定義は変更しない。`tools/validate-plan11-9-player-quality.ps1` は実表示経路の肖像・表情合成・解放、タイトルからの初回表示、BGMとフォーカスを検査し、外部からWindowsプロセスの使用メモリを測定する。`tools/audit-plan11-9-audio.py` のPCM検査は人による実聴の代替としない。

庭の環境音は天候切替でフェードし、通常画面のフォーカス喪失では一時停止する。生活SEは古い音を復帰後に持ち越さない。メニュー越しの復帰、スロット読込時の停止、見守り中の継続再生を `environment-audio` と通常のPlayer品質検証で確認する。

`tools/record-plan11-9-quality.py` で実測ログ・画像保持数・音源検査・人物別検証・残課題を検証結果JSONへ記録する。初回ページと通常ページ、試験用AssetBundleと製品Resources、テクスチャ容量推定とプロセス使用メモリを混同せず、基準未達を成功に書き換えない。

性能測定時は録画・別ゲーム起動などの外部負荷を測定条件として記録する。不明な条件は不明と記し、単発の長いフレームをゲーム不具合と断定しない。繰り返し測定は遅かった結果も含めて履歴を保持する。
